# 06 — Redesign: from point of sale to ERP

**Status:** design draft for review. No code written yet.
**Source:** requirements session with the business owner, 2026-09-20.
**Baseline:** `main` at `d76bdb1`.

The business vocabulary is Arabic and the owner's terms are authoritative. Section 2 maps
each Arabic term to the identifier the code will use; everywhere else this document uses the
English identifier.

---

## 1. Summary

The company does three things: **manufacturing, renting and selling**. The system today
covers **retail selling** only, and covers it well. Renting and manufacturing do not exist
at all. HR, payroll, invoicing and accounting reports are also wanted.

### Architectural decision 1 — a ledger at the centre

While describing the business the owner described a ledger without meaning to: *"a separate
revenue line"*, *"under current assets"*, *"its value leaves the system"*, *"counts as income"*,
*"counts as an outgoing"*. Those are **accounting postings**.

What connects every requested module is not renting — it is **the posting**. Rent, overdue,
maintenance, scrap, salaries and invoices all end up in the same place. Build each module with
its own separate reports and the result is disconnected islands with contradictory numbers,
and an "accounting report" that can never be assembled.

**Decision:** a double-entry ledger at the centre, which the modules post to automatically.
**The user never writes a journal entry by hand** — this is an operational system that posts,
not an accounting package.

### Architectural decision 2 — renting does not run on the till

The existing sync has one direction: **catalog down, sales up**. The till works offline
against an IndexedDB replica and pushes its sales when the network returns.

Renting needs none of that. A contract is a signed document with legal weight, balances and
asset states are server-owned, and raising a contract is not a 30-second checkout. Renting is
a **server and back-office module**, and is not replicated to tills.

This is the single biggest risk reduction available: the most dangerous part of the system —
the sync and offline engine — **is not touched** by the largest new module.

## 3. Analysis

### 3.1 How the requirement differs from what exists

The system is built around one idea: **`Sale` is a single instantaneous event**. Goods left,
money arrived, tax was computed and a receipt printed — all in one document, append-only, with
an id generated by the till so a re-push is recognised rather than double-recorded.

What is being asked for is structurally different:

| | Selling today | Renting as described |
|---|---|---|
| Goods and money | one event | **two independent tracks** |
| Document | one, instantaneous | a chain: contract → issue note → return note |
| Going out | once | in batches, and for some lines only |
| The item | is sold and gone | **goes out and comes back** |
| Money | collected at that moment | separate voucher, and may be pending |
| Revenue | known at the time of sale | **accrues over time** and keeps changing |

**The sentence that summarises the whole design:** goods and money are separate tracks, and
the state of one never blocks the other.

### 3.2 An item is not a single quantity

`ProductStock.StockQty` is one number. That is enough for selling — the quantity goes down and
that is that — and impossible for renting, because a rented item **is not sold**: it is out and
it is coming back.

The five states:

| State | Rentable? | Still an asset? |
|---|---|---|
| **Available** | yes | yes |
| **On rent** (with a customer) | no | yes |
| **In maintenance** | no | yes |
| **Scrap** (awaiting sale) | no | yes, at a lower value |
| **Written off** (worn out or lost) | no | **no** |

This table answers the two questions asked every day: *"how many can I rent out right now?"*
and *"what are my assets worth?"*

### 3.3 An item carries four independent values

| Value | Purpose | Changes? |
|---|---|---|
| Purchase price | historic cost | fixed |
| **Book value** | total asset value | falls through write-off and scrapping |
| Total-damage price | what the customer is charged | **frozen in the contract** |
| Rental price | the revenue | **frozen in the contract** |

None of these derives from another. A pipe bought at 1,200 may carry a book value of 800 and
be charged to the customer at 2,000 if lost.

> **There is no depreciation schedule and no annual rate.** Value falls because items are
> removed, not because a periodic calculation reduces it. An item that wears out is removed
> from the system, and any money spent on it is an expense.

## 4. Constraints the design must respect

These are not opinions — they are facts about the current code, and breaking them means
rewriting work that already runs.

1. **Never block the sale.** `CLAUDE.md` states that no control refuses an action because
   stock or a subscription looks wrong; those are warnings after the fact. A credit limit and
   a pending cheque are **warnings, not blocks**.
2. **`Sale` is immutable** and its id comes from the till. Any design that requires editing a
   past sale is wrong.
3. **Sync:** a monotonic version cursor (`SyncEntity.Version`), batches of 500, and deletion by
   tombstone (`IsDeleted`). Every new entity **must decide** whether it replicates to tills.
4. **Two databases:** every schema change is 2 migration sets (SQLite in Infrastructure,
   MySQL in `AlgeriaPos.Migrations.MySql`). Both were first run live on 2026-09-23 (per
   `docs/03-work-status.md`). A third set, SQL Server, existed when this was written and was
   removed that same day — one company per deployment, one migration set fewer per change.
5. **IndexedDB is at version 5**, and upgrades reshape rows in place so an offline till keeps
   working. Any new till-side field means version 6 with a safe upgrade.
6. **The country profile is operator-owned**, and everything country-specific is a setting
   there, not a constant in code.
7. **The design system is published** (`CLAUDE.md`) and is read before any UI work. RTL via
   logical properties, no dark theme, no icon set.

## 5. Design

### 5.1 The accounting spine

```
LedgerAccount    code, nameAr/Fr/En, type(Asset|Liability|Income|Expense|Equity), isSystem
LedgerEntry      entryDate, branchId, sourceType, sourceId, description, isReversal
LedgerEntryLine  accountId, debit, credit
```

* **Double entry**, and each entry must balance — an automatic check that catches module bugs.
* **Users never write entries.** Every entry carries `sourceType`/`sourceId` back to its document.
* **Nothing is deleted.** Corrections are reversing entries (`isReversal`), exactly like `Sale`.
* A default chart of accounts is seeded; the admin can extend it.

The agreed lines:

| Line | Type |
|---|---|
| Rent (the agreed period) | income |
| **Overdue** | income — its own separate line |
| **Maintenance paid by the customer** (partial damage) | separate income |
| Maintenance you pay on your own assets | **expense** |
| Total-damage / lost compensation | compensation for an asset |
| Scrap sale | income + difference against book value |
| Write-off / internal loss | loss |
| Deposit | **liability — not income** |

> The same work (maintenance) posts as income or expense depending on **who pays**. That is
> decided at the moment of return.

### 5.2 Stock and assets

`ProductStock` splits from one number into per-state balances:

```
ProductStock   productId, branchId,
               availableQty, onRentQty, maintenanceQty, scrapQty,
               reorderLevel
               -- owned = the sum of the four. Written-off leaves entirely.
```

* **`StockMovement` keeps its shape.** `Reason` is a free string (`"sale"`, `"transfer"` today),
  so rental movements record in the same table under new reasons. A significant saving.
* **Branch transfers already work with no direction constraint** — verified at
  `POST /stock/transfers`: main↔branch and branch↔branch all work. What is added: a transfer
  may only move the **available** balance.
* Asset value: `Product.AssetUnitValue`; total assets = owned × value.

**Cross-branch availability, permission-gated**

A branch must be able to see whether an item is available **at another branch** — Oran is out
of scaffolding, the clerk checks and Algiers has 200 available, and a transfer is arranged
instead of losing the job. The owner's condition is that this is **permission-gated**, not open
to everyone.

* It shows the **available** balance specifically, not the owned total — on-rent and in-maintenance
  quantities are not something another branch can have.
* It is **read-only and reserves nothing.** Seeing stock elsewhere is not a claim on it; the
  transfer is a separate, deliberate act with its own document.
* It is an **online query, not replication.** A till's local replica holds its own branch only,
  and copying every branch's balances to every device would be both wasteful and instantly stale.
  Offline, the screen shows the local branch and says the rest is unavailable — it does not guess.

> ⚠️ **This does not fit the current permission model.** Today there are exactly three roles
> (`Cashier`, `Manager`, `Admin`) and nothing finer. "Visible to some branches but not others"
> cannot be expressed by a role, so this needs a named permission (`ViewOtherBranchStock`),
> defaulting off. With the headcount and branch count described, the three-role model is likely
> to need this anyway — but it is a real addition, not a flag on an existing screen.

**Disposal routes:**

| Route | Effect |
|---|---|
| Internal loss | write-off — a straight loss |
| Total damage at the customer | compensation from the customer **+ the wreck becomes scrap** |
| Scrap sale | asset leaves + proceeds + difference against book value |

### 5.3 The warehouse module

> **Any product — for sale or for rent — must enter the warehouse first, then be transferred
> to the branches.**

*Superseded 2026-10-12 (owner): a branch can buy from suppliers itself. Receiving now carries a
branch — a branch user's own, the Admin's choice, the main warehouse by default; see
`StockEndpoints` and docs/owner-notes.md.*

This is **not enforced today**: `POST /products/{id}/stock` accepts any branch, and the same
endpoint serves receiving, breakage and stocktake corrections alike. One generic adjustment
does every job, which is why the rule cannot be expressed.

The module splits that one endpoint into documents with distinct rules:

| Document | Where | Rule |
|---|---|---|
| **`OpeningBalance`** | any branch | **only while the branch is still in setup** |
| **`ReceivingNote`** | **main warehouse only** | new goods entering the company |
| **`StockTransfer`** (exists) | any → any | main↔branch and branch↔branch, **available balance only** |
| **Issue** (sale, `IssueNote`, scrap, write-off) | the holding location | every outward movement is a document |
| **`StockAdjustment`** (exists) | any branch | stocktake, breakage, correction — unchanged |

**Receiving and adjustment must be separated, not merged into a ban on branch entries.** A
branch counts and finds three pipes missing and has to correct it; forbid all branch entries
and stocktaking becomes impossible. The rule being enforced is *"new goods enter centrally"*,
not *"branches can never touch a quantity"*.

The receiving note is also the natural place to record **asset value and purchase price** —
without it there is no place for those numbers at all.

**Opening balances: the exception that has to exist**

> Goods may be loaded straight onto each branch **at the start**; after that they must come
> from the warehouse.

Without this the system cannot be adopted at all — on day one every branch already holds stock
that never passed through a receiving note, and forcing it through one would invent a purchase
that never happened.

* `OpeningBalance` is its own document, per branch, and it states quantity **and value**.
* Each branch is **opened for operation** by an explicit admin action. Before that, opening
  balances are allowed; after it, they are refused and the warehouse rule applies.
* Reopening is possible but is a **manager-level action with a written reason**, like the
  retroactive extension in section 5.5 — otherwise "opening balance" quietly becomes the way
  people bypass the warehouse whenever it is inconvenient, and the rule stops meaning anything.

> ⚠️ **An opening balance is not a purchase and not income.** It posts against an opening-balance
> equity account, never to revenue or cost of sales. Post it as a purchase and the first period
> shows a cost that never occurred; post it as income and the first period shows a profit that
> never happened. This is the same class of error as treating a remittance as income (section 5.8).

### 5.4 Dynamic payment methods

Today: `PaymentMethod` is a fixed enum (`Cash, Card, Credit, Mixed, GiftCard, Loyalty`) plus a
closed whitelist `SupportedPaymentMethods`. **A postal transfer is impossible today.**

```
PaymentMethodDef  key, nameAr/Fr/En, behavior, requiresConfirmation,
                  affectsCashDrawer, extraFields, isActive, sortOrder
```

| Kind | |
|---|---|
| **Built-in** (cash, card, credit, gift card, loyalty) | behaviour is programmed — `Credit` moves the customer balance, `GiftCard` the card balance, `Loyalty` the points. Can only be enabled and renamed |
| **Operator-defined** (postal transfer, bank transfer, cheque) | generic behaviour: money in, extra fields, confirmation |

**A payment now has a state:**

```
PaymentStatus = Pending | Confirmed | Bounced
```

* **Cash is confirmed immediately. Everything else is pending until confirmed.**
* Card is **confirmed by default**, because the terminal's approval number is the confirmation
  (changeable in the setting).
* Cheque: number, bank, **due date**, a "cheques due" screen, and a **Bounced** state.
* **A pending payment does not reduce the customer's balance** — the customer counts as unpaid.
  Reducing a balance against paper means extending credit on money that never arrived.
* **But release is never blocked by payment.** The customer collects normally. (Consistent with
  "never block the sale".)
* **A pending payment stays out of the cash drawer** in the Z-report, or the drawer shows a
  shortfall on every day with a cheque.

> This is the highest-risk item in the plan: it changes payment storage in **sales** too, not
> just renting — 2 migration sets plus IndexedDB. It is done **once**, in phase 1.

### 5.5 Renting

```
RentalContract       number, customerId, branchId, status(Open|Closed),
                     lockedAtUtc, signedAtUtc, depositAmount*, notes
RentalContractLine   productId, qty, durationDays,
                     rentUnitPrice, damageUnitPrice, lateUnitPrice,
                     parentLineId          -- for the accessory line
IssueNote(+Line)     contractId, issuedAtUtc, branchId | lineId, qty
ReturnNote(+Line)    contractId, returnedAtUtc | lineId, qtyOk,
                     qtyPartialDamage, maintenanceValue, qtyTotalDamage, qtyMissing
ContractExtension    contractId, lineId?, extraDays, unitPrice,
                     isRetroactive, approvedByUserId, reason
RentalCharge         contractId, kind(Rent|Late|Maintenance|Damage|Missing), amount
```
`*` deposit fields are built and left **switched off** (section 5.6).

**Contract rules**
* By quantity, with several lines.
* **Locked against editing as soon as its first issue note is raised.**
* Carries three **signed** prices per line: rent, total damage and **overdue**.
  (The overdue price must be signed with the others, or there is nothing to stand on when the
  customer refuses to pay the difference.)
* **It has no end date.** Duration is a property of the line.
* **It closes when the last return note clears what is out.** Precisely: for each line,
  *quantity issued = returned + settled as lost/damaged*. Quantities never issued have no
  bearing on closing.
* Each line carries three numbers: **contracted / issued / left to issue**. Issues never exceed
  the contracted quantity.

**Calculation rules**
* **The period starts at the issue note date**, not the contract date.
* The unit of calculation is **(line × issue batch)**. Each batch gets its full duration from
  the day it went out.
* **Matching returns to issues: FIFO** — oldest closes first. The items are quantities, not
  serialised, so there is no other way to know which pipe came back. *(decided — section 7)*
* **A return may be taken at a branch other than the issuing one.** When that happens the
  system records an **implicit transfer** between the two branches, otherwise one branch ends up
  holding stock it never received and the balances drift. *(decided — section 7)*
* **Pro rata by days, with a one-day minimum.**
* **Daily rate = monthly price ÷ 30 fixed** (a commercial month). Dividing by the actual days
  in the month makes the same period dearer in February, and there is no convincing answer when
  the customer asks.
* Days = return date − issue note date, minimum one.
* **The full period is invoiced when the goods are issued** *(confirmed 2026-09-23)*. Everything
  else follows from this: the refund below has nothing to refund otherwise.
* **Early return** refunds the unused period through a **`PaymentVoucher`**. If the customer is
  on account and has not paid, it reduces the debt instead and no voucher is raised.
* **A unit that never comes back still accrues rent** for the days it was on site, on top of the
  frozen damage price *(confirmed 2026-09-23)*. The customer had the use of it and then did not
  return it; the hire and the asset are separate charges.
* **Rent stops the day the customer reports the loss** *(confirmed 2026-09-23)*. Reporting is
  what lets the company write the unit off, charge for it and stop waiting for it. A customer
  who says nothing keeps paying to the day the loss is finally settled, because the company did
  not know it was gone and could not re-hire it — and because otherwise reporting late would be
  the cheaper option. The report date applies only to a note where **nothing came back**: a unit
  that walked back in was the customer's to use until they returned it, whatever was reported in
  between, so a loss is declared on its own note.

**Extension is not overdue**

| | Extension | Overdue |
|---|---|---|
| Signed document | yes | no |
| When | **before** the period ends | computed automatically at return |
| Price | the rental price | **a higher price set by the admin** |
| Line | rent income | overdue income |

* **An extension is a decision; overdue is a consequence.**
* An extension is a **separate document**, not an edit to the contract, so the "contract locks"
  rule holds. It causes **no stock movement** — the goods are already on site.
* Raising a new contract instead would force a **fictitious return and a fictitious issue** for
  goods that never moved, which corrupts the most important report: *what is out, and with whom*.
* **Retroactive extension** is allowed, but requires **manager permission** (`UserRole.Manager`
  or above already exists) and a written reason. Left open to everyone, every overdue becomes an
  extension and the line loses its meaning.
* The overdue price is **a multiplier on the rental price** (e.g. 1.5×), set by the admin, with
  a per-item override — it stays correct on its own when prices change, instead of needing a
  second price table kept in step. The resulting figure is still frozen and signed on the
  contract. *(decided — section 7)*

**Accessory lines**
* Go out by count with the main item (a scaffold → 10 couplers + 5 posts).
* **Rental price zero, total-damage price mandatory.** "No value" applies to the rent line only,
  never to compensation. If the scaffold comes back 40 couplers short, those are charged.
* **An accessory inherits its parent's end date** — it comes back on the same return note, and
  a coupler expiring before the scaffold it is bolted to makes no sense. *(decided — section 7)*
* **A component list on the item** generates them automatically on the issue note, editable.
  This is what stops a part being forgotten at issue — which is exactly why returns come back
  short with nobody able to say why.
* That same component list is the mechanism **manufacturing** will need for its recipe. Built
  once, used twice.

### 5.6 Deposit: built, not switched on

There is no deposit today, but it must exist in the system and stay off.

* The fields go into the schema **now**, alongside the rest of the rental tables.
* One switch, **off by default**.
* While off it is **invisible** — no empty field, no zero line, no report column.
* When switched on: **a liability, not income**.

**Why build it early:** adding an empty column now, with the rest of the tables, is free.
Adding it later is 2 migration sets against databases holding live customer data.

### 5.7 Selling

| Requirement | State |
|---|---|
| Invoice discount by **percentage or amount** | ✅ **already built and working** |
| Prices **excluding** tax | ⚙️ setting exists, **currently set wrongly** |
| Choosing **taxed / untaxed** per invoice | 🔨 new |
| Keeping untaxed invoices out of tax reports | 🔨 new |

* **The discount is already done correctly:** `money.ts` distributes an order-level discount
  **across the lines pro rata** before tax, so each line's tax is computed on its discounted
  base. That matters because one invoice carries several rates (19%, 9%, 0%); a lump sum taken
  off the bottom would corrupt the tax breakdown. Rounding is handled too — the remainder lands
  on the last line.
* **`PricesIncludeTax` — done on 2026-09-25.** The Algeria preset now ships `false`: the
  owner's prices are net and the tax is charged on top. Concrete at 12,000 used to mean the
  customer pays 12,000 with 1,916 of tax inside it; it now means 12,000 + 2,280 = **14,280**.
  The price list was already net, so nothing was repriced — only its reading was corrected.
  The till was the last screen still carving the tax out from inside; the invoice screen had
  always added it on top.
* **Invoice type** (`Taxed | Untaxed`) is chosen at creation; an untaxed invoice has no tax line
  and no rate breakdown.
* **It must be separated in reporting from the start:** the tax report sees taxed invoices only.
  That is not extra work, but it has to be built in rather than patched later.
* **An invoice typed in the back office and its goods (P0.3, 2026-11-09) — a setting, off by default.**
  The accountant's choice sits in Reports › Stock valuation ("An invoice typed in the back office",
  `StockValuationSettings.DirectInvoiceStock`, `accounting.manage`). Off, a direct invoice posts
  411 / 70x / 4457 and nothing else, as it always has. On, each line whose product tracks stock (a
  line billed by the day is hire and moves nothing) takes its quantity out of the invoice's branch —
  a movement of kind `InvoiceSale`, never refused for a shortfall, as at the till — and the invoice's
  own entry adds Dr 600 / Cr 310 at the cost in force: the cost price, or the weighted average once
  sales are costed at it (C-01), falling back to the cost price where there is no average. The line
  keeps that cost. A credit note made by hand then asks, per line, how much came **back into stock**
  (0 by default: a credit of money only; at most what the note credits and what the line took out
  less what came back); those goods come back (`InvoiceReturn`) at the line's own cost, Dr 310 /
  Cr 600 in the note's entry. The setting is read when an invoice is issued: an invoice issued while it
  was off is never revisited, and its goods cannot come back through a credit note. Typed invoices
  have been closed at the route since 2026-10-10, so the setting acts only if that route reopens.

### 5.8 Cash boxes and remittance to the main branch

Nothing in the system tracks where cash physically is. Sales record a payment method, the
Z-report counts a drawer, and there it stops. But the owner's actual process is:

> The manager goes to the branch and collects the takings. The branch records an **outgoing**
> under the line **"remittance to the main branch"** for that amount.

So cash has a **location**, and it moves between locations.

```
CashBox        branchId, nameAr/Fr/En, isMain, isActive
CashMovement   cashBoxId, direction(In|Out), amount, kind, occurredAtUtc,
               relatedCashBoxId, sourceType, sourceId, userId, reference, note
```

* Paired rows, exactly like `StockMovement` with its `RelatedBranchId`: **Out** at the branch
  and **In** at the main branch, linked by `relatedCashBoxId`. The pattern already exists in
  this codebase and already works for transfers, so it is reused rather than reinvented.
* A **remittance** (`توريد للفرع الرئيسي`) is the document the manager raises on collection. It
  carries who collected, when, and how much, so an amount that never arrives has a name against it.
* Every branch has a cash box; the main branch's is the central safe.

**The accounting rule that must not be got wrong:**

> A remittance is **not income at the main branch and not an expense at the branch**. It is a
> movement between two asset accounts. The revenue was already recognised when the sale
> happened.

The branch calls it *صادر* because money left its box, and that is the right word for a cash
report — but *صادر/وارد* describes **direction at a location**, while income/expense describes
**profit and loss**. They are different axes. Post a remittance as an expense at the branch and
income at the main and the P&L is inflated on both sides while the real profit never changed.

* The branch cash report shows it as an outgoing under its own line, as the owner described.
* The ledger posts branch cash → main safe, and the P&L does not move.

**Two consequences elsewhere:**

* **Pending payments never enter a cash box.** A cheque is not cash in a drawer, so it cannot be
  remitted and must not appear in the Z-report's cash figure (section 5.4).
* **The Z-report gains a counterpart:** the drawer can now be reconciled against
  *opening + cash sales − remittances = expected*, which is the check that actually catches a
  shortfall. Today there is nothing to reconcile against.

### 5.9 Sync and offline

| Entity | Replicated to tills? | Why |
|---|---|---|
| Rental contracts and notes | **no** | back office, server, signed documents |
| State balances | partly | the till only needs **available**, and only if it sells |
| **Payment methods** | **yes** | the till needs them at payment → **IndexedDB v6** |
| Chart of accounts and entries | **no** | server only |
| Employees and payroll | **no** | back office |

**Net result: renting does not touch the sync engine.** The only till-side change is payment
methods.

### 5.10 Reporting

This is the payoff for decision 1. Reports are **views over the ledger plus operational data**,
not figures each module totals for itself. Built the other way, a product report and an
accounting report will disagree and nobody will be able to say which is right.

Two rules hold for every report below:

* **Everything drills down to its source document.** Each `LedgerEntry` carries
  `sourceType`/`sourceId`, so a number in a report is always traceable to the contract, sale,
  issue note, remittance or payroll run that produced it. A total nobody can explain is a total
  nobody trusts.
* **Branch and period are dimensions everywhere**, because `LedgerEntry.branchId` is part of the
  spine and the owner runs several branches with their own wage bills and cash boxes.

**Accounting**

| Report | Source |
|---|---|
| Trial balance | ledger |
| Account statement / general ledger | ledger |
| Profit and loss, by period and by branch | ledger |
| **Net profit — consolidated, or for one branch** | ledger |
| Balance sheet | ledger |

> **Consolidating is not adding the branches up.** Movements *between* branches have to be
> eliminated or they are counted twice. A remittance is already safe because it posts as an
> asset transfer and never reaches the P&L (section 5.8) — but a stock transfer valued at cost
> would double-count if each branch booked it, so inter-branch movements are marked as such
> and dropped at consolidation. Getting this wrong produces a group profit that is simply
> larger than reality, which is the single most common error in multi-branch reporting.
| **Income and outgoings** (*واردات وصادرات*) | ledger, cash view |
| Tax report | **taxed invoices only** (section 5.7) |

**Vouchers and documents** (*سندات*)

| Report | Contents |
|---|---|
| Receipt and payment vouchers register | every `ReceiptVoucher` / `PaymentVoucher` with its source |
| Cheques | pending, **due** (by due date), collected, **bounced** |
| Branch remittances | who collected, when, how much, and whether it arrived |

**Product report**

Beyond movement and profitability, a rented item needs figures a retail system never asks for:

| Figure | Why it matters |
|---|---|
| Movement card: in, out, balance **by state** | the five states of section 3.2 |
| Sales profitability (price − cost) | ordinary |
| **Rental revenue per item** | which items actually earn |
| **Utilisation** — % of the period the item was on rent | an item idle 80% of the year is capital doing nothing |
| **Cumulative maintenance cost** | answers *repair it again, or replace it?* |
| Loss and damage, customer vs internal | one earns compensation, the other is a straight loss |
| Dead stock | never moved in the period |

**Branch report**

| Figure |
|---|
| Sales and rental revenue |
| **Branch result** — revenue − expenses − its own wage bill |
| Cash: opening, takings, remittances, closing |
| Stock by state |

> **A note on volume.** With the headcount and transaction rate described, reports cannot be
> written as loops over documents. They read from the ledger with indexed period/branch/account
> filters, which is a second reason the spine exists.

### 5.11 Migrations

Every phase is **2 migration sets** (SQLite for development and tests, MySQL for production)
plus an IndexedDB upgrade if the till is affected. Both providers were first run live on
2026-09-23 (`docs/03-work-status.md`). SQL Server was a third set until it was removed the same
day: the system runs at one company, and a third set per phase bought nothing.

## 6. Implementation plan

Each phase ships **working and verified** on its own, against the full suite (backend and
frontend tests, the production build, and the relevant `tests/e2e/*.cjs` scripts).

| # | Phase | Contents | Why here |
|---|---|---|---|
| **1** | **Financial foundation** | dynamic payment methods + payment states (pending/confirmed/bounced) + cheques + taxed/untaxed invoices + flipping `PricesIncludeTax` (done 2026-09-25) + **cash boxes and branch remittance** | the riskiest change, and it touches existing sales. Done **once**, up front, rather than twice. Cash boxes belong here because they share the Z-report and the pending-payment rule |
| **2** | **Stock and assets** | the five item states + asset value + `ReceivingNote` split from adjustments + write-off/scrap/maintenance + **cross-branch availability and the named permission it needs** | renting is impossible without it |
| **3** | **Ledger** | accounts and entries + posting from sales, receiving and write-offs + the first accounting reports | **before renting**, so renting posts from day one instead of being unpicked later |
| **4** | **Renting** | contract, notes, extension, day-based calculation, overdue, damage | the largest module; builds on 1–3 |
| **5** | **Invoices and statements** | invoice with due date + partial payments + credit notes + customer statement + debt ageing | the customers are contractors on account with million-dinar limits |
| **6** | **HR and payroll** | employee (not a login) + contracts + attendance + leave + **a configurable payroll engine with an Algeria preset** | independent; can run in parallel |
| **7** | **Manufacturing** | recipe + work order + raw vs finished + costing | **deferred by explicit decision** — "not now" |

**Why the ledger precedes renting:** renting generates the widest range of postings (rent,
overdue, maintenance, compensation, scrap). Built first, it would have to be unpicked and
rewired.

## 8. Payroll, HR and manufacturing

### 8.1 Manufacturing — deferred

**The owner's decision: "not now."** No details were given, and it will not be designed on
assumptions.

The one thing reserved for it: the **component list** (section 5.5) that generates accessory
lines on an issue note is **the same mechanism** manufacturing needs for its recipe. It is built
once, during the renting phase, and manufacturing builds on it later.

### 8.2 Payroll

**Decision: a payroll engine driven by configurable rules, with a ready Algeria preset.
No figure is hard-coded.**

This follows the project's founding rule — *everything country-specific is a setting, not code* —
and the pattern of the existing country profiles (DZ, MA, TN, FR, SA) that already govern
currency, tax and fiscal identifiers. Algeria works today, another country is configured from
the screen, and a change in the finance law is a setting change rather than a new build.

**What the engine must carry:**

| Element | |
|---|---|
| Base wage | by grade/post |
| Allowances | transport, meal, post, hardship, performance |
| **CNAS** | employee share + employer share |
| **IRG** | progressive income tax scale |
| Deductions | advances, absences, penalties |
| Overtime | at rates by time of day |
| **SNMG** | the guaranteed minimum |

> ⚠️ **Rates and scales are not written from general knowledge.** They change with each finance
> law, and this system computes real people's pay — a wrong figure means an employee is underpaid
> or a CNAS declaration is wrong. The numbers come from the owner or their accountant and are
> stored as reviewable settings.

**Built (2026-09-23):** `AlgeriaPos.Application/Payroll` carries `PayrollSettings`, its validator
and an Algeria preset, with tests.

* The preset states the **CNAS split — 9% employee, 26% employer** — which has been stable for
  years and is the one statutory figure it is safe to ship.
* It deliberately ships the **IRG scale empty**, the minimum wage at 0, allowance amounts at 0 and
  overtime multipliers at 1. An empty scale withholds nothing, which is obvious on the first
  payslip and gets fixed; a scale written from memory looks authoritative and is quietly short
  every month. `NeedsReview` stays set until someone with the current law confirms them.
* The validator refuses the mistakes that do not announce themselves: a tax scale with a ceiling
  on its top step (which taxes nothing above it), overlapping brackets, an overtime multiplier
  below 1, and duplicate keys.
* `SubjectToCnas` / `SubjectToIrg` per allowance are preserved exactly as configured and never
  normalised, because which allowances enter which base changes both net pay and the declaration.

**Who may change what (2026-09-23).** Everything is configurable, but not by everybody, and the
split is enforced in `PayrollOwnership` rather than left to whichever endpoint happens to sit in
front of it — a second screen, an import or a later API cannot route around it by accident.

| Owner | Fields |
|---|---|
| **Platform operator** (super admin) | contribution rates, the income-tax scale, the minimum wage, their labels, the country, and the review flag |
| **Company administrator** | the allowances this business pays, its overtime rates, its attendance mode, its working day and hours |

A company setting its own meal allowance is ordinary administration. A company editing the CNAS
rate is not: the figure comes from law, it is the same for every company in the country, and a
business that finds its contributions inconvenient must not be able to quietly lower them. This
is the division the product already draws — the operator owns the country profile and its tax
rates, the company owns its store settings and its loyalty programme — applied to payroll.

An attempt to move a statutory figure is **refused, not ignored**. Keeping the permitted half of
an edit and silently discarding the rest would leave the administrator believing they had lowered
a rate, and the first sign otherwise would be a payslip disagreeing with the screen they saved.

The operator may set anything, since they provision companies and answer for the figures — but
correcting one does not clear `NeedsReview` unless they say they checked it against the law, and
their edit is validated like any other: owning a figure is not permission to leave it in a state
that pays people wrongly.

Still to come with the module itself: the employee record, attendance capture, the payroll run
and its ledger posting, and the operator and company screens for editing these figures.

**Answered: both pay bases are needed.** The company employs **daily-paid workers and monthly
staff side by side**, so the engine carries a pay basis per employee rather than one company-wide
mode:

* **Daily** — pay derives from days actually worked, so attendance is the input and a missing
  day simply is not paid. These are typically site workers whose headcount moves week to week.
* **Monthly** — pay is a fixed figure and absence is a deduction against it.

Both feed the same deduction and contribution engine (CNAS, IRG, advances); only the gross
calculation differs. Attendance therefore cannot be optional — the daily basis depends on it.

**Answered: both attendance modes are supported, and the admin chooses.**

| Mode | How days reach payroll |
|---|---|
| **Recorded** | real clock-in / clock-out entries |
| **Declared** | a period total entered by hand (a foreman submits the days worked) |

A company default with a **per-employee override**, because the two pay bases pull in different
directions: site workers on a daily basis are the ones whose days actually vary, while monthly
staff are usually a fixed figure with absences deducted.

"Declared" is still a real input, not the absence of one — a daily-paid worker always needs a
number of days from somewhere. The setting decides whether that number is captured by the system
or asserted by a supervisor; the second carries no audit trail of its own, which is why it
should stay a deliberate choice rather than a default nobody picked.

**Answered: allowances are admin-defined, and each can be a fixed amount or a percentage.**

An allowance is therefore a **definition**, not a fixed set of columns:

```
AllowanceDef   key, nameAr/Fr/En, calculation(FixedAmount|PercentOfBase),
               value, isSubjectToCnas, isSubjectToIrg, isActive, sortOrder
```

* The admin adds, renames, enables and disables them — transport, meal, post, hardship,
  performance and anything else — without a code change. This is the same pattern as the
  dynamic payment methods in section 5.4 and the country profiles that already exist.
* A per-employee amount overrides the definition's default, since allowances are commonly
  negotiated individually.
* **`isSubjectToCnas` and `isSubjectToIrg` are not decoration.** In Algerian payroll some
  allowances enter the contribution and tax base and others do not, and getting that wrong
  changes both the employee's net pay and the CNAS declaration. Which flag each allowance
  carries comes from the owner's accountant, not from this document.

**Answered: overtime is admin-defined too.**

```
OvertimeRuleDef  key, nameAr/Fr/En, appliesTo(Weekday|Night|WeeklyRest|PublicHoliday),
                 multiplier, isActive
```

Rates in Algeria differ between ordinary hours, night hours, the weekly rest day and public
holidays, and those rates move with the law. As a definition the admin maintains, the company
sets its own bands and another country is configured rather than coded — the same approach
taken for allowances, payment methods and country profiles.

The hours themselves come from attendance, so overtime is only as good as the attendance mode
chosen above: under **Declared**, overtime hours are asserted by a supervisor along with the days.

#### The shape this all takes

Every payroll element the owner has described is **a definition the admin maintains**, never a
hard-coded rule: pay basis per employee, attendance mode, allowances, overtime bands, and the
CNAS/IRG figures. What ships is an **engine plus an Algeria preset**, which is precisely the
existing country-profile pattern applied to payroll.

**Answered: the headcount is large.** That is a design input, not a footnote, and it rules
several things out:

* **Payroll is a batch run, not a per-employee screen.** A `PayrollRun` covers a period and
  processes everyone, with states **draft → approved → posted** and a reversal path. Nobody
  opens a thousand records one at a time, and a run that cannot be reviewed before it posts
  cannot be trusted.
* **Attendance needs bulk entry.** Site workers are counted by crew, not individually — a
  foreman submits a sheet for a site and a period. A screen that takes one employee at a time
  guarantees the data never gets entered.
* **The ledger gets one entry per run, not one per employee.** Posting a thousand employees
  individually every month would bury every other transaction in the ledger within a year.
  The run posts a single balanced entry with lines by account (wages, CNAS employer, CNAS
  employee, IRG payable, net payable), and the per-employee detail stays in the payroll module
  where it is queried by employee anyway.
* **The calculation must not be written as one query per employee.** With this headcount an
  N+1 payroll run turns a monthly close into an outage. The engine loads the period's inputs in
  bulk and computes in memory.

**Answered: salaries are allocated to branches.** Each employee belongs to a branch and the
cost lands there, so a branch's result carries its own wage bill instead of everything pooling
at head office. The payroll run's ledger entry therefore posts **per branch**, not as one lump —
which also keeps it consistent with `LedgerEntry.branchId` already being part of the spine
(section 5.1).

### 8.3 HR

Today's `User` is **a login account, not an employee**: no hire date, no national id, no branch,
no contract, no attendance, no leave. The module is from zero, and it precedes payroll because
payroll reads from it.
